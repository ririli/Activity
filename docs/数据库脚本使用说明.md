# 数据库脚本使用说明

本次脚本依据需求 V1.2 和持久层设计 V2，面向 **MySQL 8.4**，只负责初始结构。仓库中尚无真实数据库连接配置；未创建业务账号、未插入活动配置、未实际执行建库建表。

## 1. 文件及执行顺序

|顺序|文件|内容|
|---|---|---|
|1|`deploy/local/mysql/000_databases.sql`|建立3个逻辑库，使用 utf8mb4_0900_bin|
|2|`services/identity-service/migrations/001_initial.sql`|账号、登录会话、Outbox，共3表|
|3|`services/activity-service/migrations/001_initial.sql`|核心配置、状态、奖励及技术表，共16表|
|4|`services/activity-service/migrations/002_records.sql`|四类记录各4分表，共16表|
|5|`services/ranking-service/migrations/001_initial.sql`|积分、排名、结算、Outbox、Inbox，共7表|
|6|`deploy/local/mysql/verify_schema.sql`|只读查看表数量、分表及约束|

合计42张物理表：账号库3张、核心库32张、榜单库7张。通知服务本次不建立业务库。

每份 SQL 中已有目标库 `USE`。建库需要建库权限，服务表迁移使用对应库的迁移账号；业务运行账号后续独立配置，仅授予本服务所需权限，不使用建库账号运行服务。

这是空库初始迁移。表使用普通 `CREATE TABLE`，重复执行会报错，以暴露重复迁移或结构漂移；不靠 `IF NOT EXISTS` 掩盖差异。DDL 有隐式提交，整个文件并非一笔可回滚事务；中途失败应核对已创建对象后修复，不能直接重跑或批量删库。

## 2. 如何执行

可以用数据库客户端逐个打开并执行上表中的 SQL。也可以连接 MySQL 命令行后，逐条输入下列命令；**这些是 mysql 提示符中的命令，不是 PowerShell 命令**。每步确认没有错误后再继续：

```sql
SOURCE D:/gopath/src/Activity/deploy/local/mysql/000_databases.sql;
SOURCE D:/gopath/src/Activity/services/identity-service/migrations/001_initial.sql;
SOURCE D:/gopath/src/Activity/services/activity-service/migrations/001_initial.sql;
SOURCE D:/gopath/src/Activity/services/activity-service/migrations/002_records.sql;
SOURCE D:/gopath/src/Activity/services/ranking-service/migrations/001_initial.sql;
SOURCE D:/gopath/src/Activity/deploy/local/mysql/verify_schema.sql;
```

所有应用连接都应设置 UTC 时区及严格 SQL 模式，例如包含 `STRICT_TRANS_TABLES`；脚本设置的会话时区不会自动影响后续应用连接。日期字段采用 `DATETIME(6)`，读写约定为 UTC；榜单单独保存业务发生的秒级时间。

## 3. 四分表生成与检查

`002_records.sql` 从 `migrations/templates/002_records.sql.tmpl` 生成。模板仅用于生成，不直接导入数据库。后缀对应 `user_id % 4`，每张表另有 CHECK 防止误路由。未启用跨表外键，跨表归属、完整性及写入顺序由应用事务和核对保障。

以下是 **PowerShell** 命令：

```powershell
# 初始脚本发布前，修改模板后重新生成16张记录表的DDL。
& 'D:\gopath\src\Activity\scripts\Generate-RecordMigrations.ps1'

# 检查生成文件与模板、表数量、主键及路由约束；不连接数据库。
& 'D:\gopath\src\Activity\scripts\Check-Migrations.ps1'
```

首次部署以后不要修改已执行迁移或重新生成已发布的002；变更应新增编号迁移，并同步修改4张物理表。当前未选定迁移框架，执行版本记录应由后续迁移工具接管。

静态检查不等于 MySQL 语法与事务测试。当前环境未发现可直接使用的 MySQL 服务端、客户端或 Docker 命令，本次仅完成静态核对；真实实例仍需验证建表、错误分片拒绝、重复唯一键、事务回滚及查询执行计划。

## 4. 字段与实现约定

- ID 采用应用生成的全局唯一正整数，数据库为 `BIGINT UNSIGNED`，本次不使用自增；H5 输出字符串。业务数量和金额使用有符号 `BIGINT` 并检查非负，资产流水增减允许负数。
- 普通抽奖 `mode=NORMAL`，先抽后付兑现 `mode=PREVIEW`；预览生成不会写正式表。池代码为 `DAY/NIGHT`。
- 正式单增加 `unit_petal_cost` 价格快照，便于数据库校验实际消耗、申请预扣和退款，不将5/100固定成所有活动的永久单价。
- 账号名暂按大小写敏感存储，应用不得一边归一化一边按原值查询；最终账户大小写规则应在注册接口定稿时统一。格式检查与限流时序由应用实现。
- 奖励状态为 `OBTAINED/PENDING_CHOICE/SELECTED`，宝箱状态为 `OPENED/CONFIRMED`；二者分开。原快照不随选款重写，不用 SQL 触发器实现发奖或开奖。
- 预览的确认、放弃状态列互斥，支付与原结果兑现必须同事务；SQL 不会自动检查活动时间或随机规则。
- `idempotency_request` 仅保存已成功的普通抽奖，窗口按首次接纳起24小时约束。过期仍保留记录拒绝旧标识复用；首次接纳与结果在同一成功事务提交。
- 资产流水按“本批金币中奖、本批花瓣中奖”等原因汇总，不为每抽增加资产流水；奖励明细和逐抽明细仍逐抽保存。余额链、批次汇总和跨表点亮总数需应用校验。
- 阶段位图按3、5、8、11、15、17朵分别对应 bit 0～5；轮状态 `ACTIVE/FULL/COMPLETED` 中 `COMPLETED` 指开启下一轮时关闭旧轮，不等同于活动结束。
- Outbox 和结算任务预留租约字段供多实例抢占、超时恢复；Inbox 必须与消费变更同事务提交。

规则 JSON 格式、生效策略、初始花瓣流水补全不在本次 DDL 中擅自固定；未提供自动发奖数据、测试用户或活动静态日期。注册资产通过业务初始化，不用钱包列默认值发放，以免重复赠送。

SQL 语法约束参考 [MySQL CREATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/create-table.html) 和 [CHECK 约束说明](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html)。本方案使用的 CHECK 需要目标实例实际强制执行，不适用于忽略 CHECK 的旧版本。
