# 整点榜单结算

## 业务口径

`EDITION_HOURLY_RANKING=true` 在创建新期次时启用。有效整点严格位于活动开始和结束之间，按北京时间取整，数据库和消息使用 UTC 时间。整点前受理并最终提交的正式抽奖计入该整点，恰好在整点受理的计入下一窗口。参与初始化产生 0 分记录。每整点按累计积分降序、达分秒升序、用户 ID 升序取前 100 名，每人获得 1,000 花瓣。活动结束继续由原有 MySQL 最终榜发奖。

## Barrier、封账和 Redis

1. 榜单调度协程在期次整点将任务和 `HourlySettlementBarrier.v1` 写入榜单库。Outbox 发布到现有 RabbitMQ 交换机，`ranking.facts.v1` 消费者提交 `WAITING_WATERMARK` 后确认消息并通知结算协程。未收到回执的 Barrier 在发布 30 秒后可用原事件 ID 重投。重启后调度协程补齐到期窗口，结算协程扫描待处理状态。
2. 活动服务以数据库时钟受理抽奖，在原事务中持有窗口分片共享锁。写入方在事务末尾给事实分配序号，与抽奖及 Outbox 一起提交。每片有 16 组序号，用户固定属于一组。封账接口对旧窗口取排他锁，等待跨点事务完成，再返回四片各组水位。新窗口独立受理。
3. Redis 分片使用 `user_id % 4`。整点键格式为 `ranking:<环境>:{<期次>:<分片>}:hourly:<截止秒>:board`。窗口只维护有变化用户的期次累计分。正常有旧、新两个窗口，积压时旧窗口按截止时间独立保留。消费者及后台任务按连续序号补齐，同一窗口按活动库 Outbox 回放。已发布事实保留在 Outbox 中，支持 Redis 重建。
4. 四片分别用 Lua 校验代次和完整水位并冻结 Top 100。榜单服务用这四份候选和上一整点名单计算新名单。新名单与待发记录一起提交后，旧 Redis 窗口由清理协程退役。实时榜采用同样的四片路由，Top 20 归并和本人排名沿用原有积分编码与排序规则。

现有实时榜的重建和消息消费仍按单活运行。需要额外结算进程时，设置 `RANKING_HOURLY_WORKER_ONLY=true`，使用相同数据库和 Redis 分片配置以及独立 `NODE_ID`。额外进程通过扫描任务接管封账与发奖，实时榜和 RabbitMQ 消费由主实例负责。

## 数据与发奖恢复

| 服务 | 数据 | 用途 |
|---|---|---|
| 活动 | `hourly_ranking_window`、`hourly_ranking_sequence` | 封账和已提交序号 |
| 活动 | `outbox_event.uk_hourly_fact` | 按窗口、分片、序号组和序号回放 |
| 活动 | `hourly_ranking_grant`、`reward_grant`、`wallet_ledger_*` | 幂等奖项、奖励明细及资产流水 |
| 榜单 | `hourly_settlement`、`hourly_award` | Barrier 回执、水位、冻结名单及到账进度 |

结算与发奖按数据库租约认领，过期后可接手。发奖请求使用 `settlement_id` 和 `user_id`，钱包加款、奖励明细和流水同事务提交。响应丢失后重试返回同一个 `grant_id`。所有获奖者确认到账后任务进入 `COMPLETED`。调度和发奖日志记录延迟，正常负载的到账目标为整点后 60 秒。

## 开发验证

按 [本地部署](../deploy/local/README.md) 应用迁移。在隔离环境设置 `ACTIVITY_TEST_MYSQL_DSN`、`RANKING_TEST_MYSQL_DSN`、`RANKING_TEST_REDIS_ADDR`、`RANKING_TEST_PREPARED_SCHEMA=1`，运行活动和榜单服务的 Go 测试。提供 `RANKING_TEST_AMQP_URL` 时，Barrier 用例经过实际 RabbitMQ 发布和消费。重点检查跨点提交、回滚后的水位、乱序回放、Redis 丢键重建、同分同秒第 100/101 名以及发奖响应丢失后的补发。
