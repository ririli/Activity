# Activity 项目开发规划（DDD 微服务）

日期：2026-11-04  
需求依据：《Lottery业务需求文档（不含后台）》V1.1  
定位：开发范围、领域划分、服务边界与实施顺序的初步规划，不展开接口和数据库详细设计。

## 1. 目标与范围

以 Go 实现活动后端，采用 DDD 分层与微服务架构，复现现有用户业务，同时保证资产正确、结果可恢复、重复请求不重复产生收益。

- 本期覆盖账号、资产兑换、双奖池抽奖、花朵与轮回、阶段奖励、宝箱、选款、先抽后付、记录、榜单、弹幕和结束结算。
- 暂不分析或改造 `web` 下的 H5 资源，后续联调阶段再核对前端接口适配。
- 不建设后台管理系统；活动配置先通过受版本管理的初始化数据和部署流程提供，不新增管理页面。
- 不接入真实支付、真实背包、穿戴、CP 福利履约、每日任务或道具过期回收。
- 本规划中的服务和技术选型是新系统设计建议，不代表已有实现结构。

## 2. 领域划分与服务边界

先划分业务边界，再确定部署边界。限界上下文与微服务不必一一对应；强一致的上下文可以先在同一服务内协作。

|限界上下文|主要职责|初期部署归属|
|---|---|---|
|账号与身份|注册、登录、续期、退出、禁用校验、注册限流|账号服务 `identity-service`|
|活动与参与|期次、参与状态、用户轮回、花朵、保底、阶段及宝箱进度|活动核心服务 `activity-service`|
|抽奖与兑现|奖池规则、逐抽执行、预览、确认与放弃、固定结果恢复|活动核心服务 `activity-service`|
|资产与奖励|账号级金币/花瓣、兑换与限购、奖励记录、选择权益及发放|活动核心服务 `activity-service`|
|榜单与排名奖励|积分投影、Top 20、个人排名、最终排名及奖励清单|榜单服务 `ranking-service`|
|实时中奖通知|消费允许播报的获奖事件、维护连接、推送弹幕|通知服务 `notification-service`|

**初期采用四个业务服务。** 抽奖、资产和参与进度保留在活动核心服务的同一数据库事务内，避免为了拆服务而引入扣费成功但发奖失败的中间状态。内部模块通过应用接口协作，禁止绕过模块直接修改其数据。

账号数据归账号服务；余额、进度、奖励与正式抽奖事实归活动核心服务；榜单数据归榜单服务；通知服务不保存中奖业务事实。各服务独立拥有数据，禁止跨服务直接读写数据库。

当资产能力需要服务多个独立业务、确有独立扩容需求时，再评估拆出资产服务；拆分前必须重新设计预留、确认、撤销和对账协议，不直接把本地事务换成远程调用。

## 3. DDD 模型与代码组织

|模块|主要聚合或领域对象|关键规则|
|---|---|---|
|账号|`Account`、`Session`|账号唯一、禁用控制、登录续期|
|活动配置|`ActivityEdition`、`RuleSnapshot`|期次状态、时间范围、奖池及规则版本|
|资产|`Wallet`、`PurchaseOrder`|账号级余额、余额非负、业务单唯一、当期限购|
|参与进度|`Participation`（用户＋期次）|当前轮次、18朵进度、累计消耗、阶段状态和宝箱状态|
|抽奖|`DrawOrder`、`PreviewOrder`|申请/实际抽数、固定逐抽结果、退款、预览状态转换|
|奖励|`RewardGrant`、`ChoiceEntitlement`|来源可追溯、权益只兑现一次、选款不可改|
|榜单|`RankingEntry`、`RankingSettlement`|积分、达到分数时间、排名快照、结算唯一性|

花瓣数量、金币数量、抽数、奖池类型、轮号、奖励来源等作为值对象表达，避免混用。轮回属于用户当期进度，不是全局活动期次；余额不放入当期进度聚合。

服务内部采用四层：

- **接口层**：HTTP/RPC、鉴权上下文、参数转换、统一错误码。
- **应用层**：用例编排、事务、幂等、并发控制、跨模块调用与事件发布。
- **领域层**：聚合、值对象、领域服务、状态转换及仓储接口；不依赖数据库或通信框架。
- **基础设施层**：数据库仓储、Redis、消息队列、随机数实现、外部服务适配。

建议采用单仓库组织，按 `services/<服务>/internal/<上下文>/{domain,application,infrastructure,interfaces}` 划分代码。公共包只放日志、通信等基础能力，不共享领域实体或数据库模型。

## 4. 核心用例与一致性方案

### 4.1 普通抽奖与奖励

1. 校验身份、活动状态和抽数，按业务请求号查询是否已有结果。
2. 在事务中锁定账号钱包及当前参与进度，校验余额、并发状态。
3. 扣除申请抽数所需花瓣，逐抽执行奖品判定、概率点亮、累计保底及节点解锁；满18朵立即停止并退回未执行部分花瓣。
4. 同一事务保存余额、实际消耗、奖励、进度、订单结果及待发布事件，提交后返回完整结果。

中奖花瓣不能用于支付本单；退款不增加积分或保底。随机能力通过接口注入，生产使用可靠随机源，测试可控制结果；保存逐抽结果与规则版本，重试读取原单，不重新随机。

阶段领取、宝箱开奖/确认、选款和开始下一轮分别建立明确用例。宝箱开出结果立即持久化，确认才增加完成次数；开启下一轮仅检查需求规定的阶段、宝箱及阶段选款条件，不额外要求清空普通抽奖选择权。

### 4.2 购买与先抽后付

- 普通补差兑换和抽奖是两笔业务：兑换提交后即生效，后续抽奖失败仍保留花瓣。
- 商店优惠档和模拟礼包通过“用户＋期次＋商品”的唯一约束实现限购；模拟礼包不调用支付、不扣金币。
- 预览持久化起点、规则版本和逐抽结果，不扣资产，不推进正式进度，不设置30分钟业务过期。
- 确认时锁定预览、钱包及参与进度，重新校验活动、正式抽奖历史和预览起点；补差、扣费和全部结果兑现必须在同一事务成功。
- 确认、放弃通过互斥状态转换处理；普通抽奖无需因存在预览而被禁止，但会使旧预览不再满足确认条件。

### 4.3 跨服务协作

- 注册完成后可靠发送账号创建事件，活动核心幂等初始化资产；注册自动登录后的业务访问必须能等待或补偿初始化，不能重复赠送。
- 使用事务 Outbox 保存业务变更和事件，消费者以事件 ID 去重；允许消息重复投递，不假设消息系统提供端到端“恰好一次”。
- 榜单消费正式抽奖的实际消耗事件，以抽奖单为单位幂等更新；使用业务发生时间及顺序信息，不能以消息到达时间决定同分名次。
- 弹幕使用独立事件映射，严格保留需求中的来源差异：普通抽奖直接戒指及普通奖励选款等规定来源才播报，不自动扩大到阶段、宝箱或先抽后付确认直接戒指。
- 实时投递失败不回滚发奖；内部事件可靠传递与用户断线后不补历史是两个不同层面的约定。

资产与奖励事实强一致；榜单和展示投影允许最终一致。Redis 用作缓存和榜单加速，数据库保存可重建的业务事实。

## 5. 期次结束与结算

由可重试的内部任务编排结算，不新增后台触发页面。参与截止与结算完成分别记录状态。

1. 关闭新参与入口，并通过活动状态检查与并发控制，等待截止前已接纳的事务完成，确定本期有效抽奖范围。
2. 从正式抽奖事实核对并补齐积分，确认榜单消费到结算水位后冻结最终排名；排序保持分数降序、达到分数时间升序（秒）、用户 ID 升序，保留0分用户规则。
3. 榜单服务持久化排名快照与奖励清单，活动核心按“期次＋用户＋奖励项”幂等发放。
4. 活动核心补发达标阶段奖励，按历史已获得/已选择奖励处理待选权益，逐份更新持有情况；完成已开奖未确认宝箱，不开启尚未开奖的资格。
5. 各步骤可断点恢复并对账，全部成功后标记结算完成；结束后的已有奖励确认按具体用例控制，不统一封禁。

多轮用户的达标未领阶段奖励也必须纳入核对。未确认预览不因结算自动改为过期，确认仍受活动状态校验。

## 6. 技术与工程建议

|方面|初期建议|
|---|---|
|开发语言|Go；建项时确定并固定兼容 SDK 与依赖版本|
|服务接口|面向 H5 使用 HTTP JSON；内部同步协作优先使用清晰的 RPC 契约|
|持久化|MySQL；核心事务、资产流水、抽奖事实和唯一约束落库|
|缓存|Redis；限流、热点配置、榜单与会话辅助，不能作为预览结果唯一存储|
|事件通信|选择一种消息队列，配合 Outbox、消费者去重、失败重试与告警|
|实时连接|通知服务提供 SSE 或 WebSocket，联调时确定与 H5 的适配方式|
|部署|先容器化、独立配置及健康检查，按实际规模决定是否引入 Kubernetes|
|可观测性|关联请求号、业务单号和事件 ID；监控扣费失败、发奖失败、事件积压与结算状态|

资产流水用于审计与对账，不代表本期新增用户资产明细页面。活动配置在生效前校验权重、阈值和奖励引用，执行时保存版本；进行中的预览不能因配置调整重新生成结果。

## 7. 开发阶段与交付物

|阶段|主要工作|交付与完成标准|
|---|---|---|
|一：领域与契约|统一术语、状态机、聚合边界、事务范围、错误码及事件契约|领域模型简图、接口草案、表结构草案；关键规则无歧义|
|二：工程与基础能力|服务骨架、配置、数据库、日志、鉴权、账号、期次及资产初始化|能注册登录、查询当前期次与余额；重复初始化无额外收益|
|三：核心业务闭环|商店、礼包、补差、普通抽奖、花朵保底、退款与业务记录|从兑换到满轮的完整流程可运行，重复和并发请求结果正确|
|四：奖励与预览|阶段奖励、宝箱、选款、下一轮、先抽后付及恢复|固定结果可恢复；确认失败无部分扣费或发奖|
|五：异步与结算|榜单、通知、结束结算、事件补偿及对账|排名可重建；重复结算不重复发奖；事件故障可恢复|
|六：联调与验收|再核对 H5 接口适配，完成业务回归、并发和故障演练|按需求第16节验收，输出部署说明及遗留问题|

先以活动核心服务形成可运行闭环，再完善榜单和通知集成。工期在阶段一完成、团队规模和接口适配工作量明确后估算。

## 8. 验收重点与待确认项

重点验证以下高风险场景：

- 默认首抽星夜点亮3朵；概率只判断一次、保底可连续补亮；两池共享进度。
- 满轮停止、实际消耗计分、未执行部分退花瓣；不自动跨轮。
- 同请求重试、并发抽奖、重复领奖和重复确认不会重复扣费或发奖。
- 预览刷新返回原结果、超30分钟仍可恢复；预览后正式抽奖使确认被拒绝。
- 宝箱不放回且固定结果可恢复；不同来源选择权按各自流程处理。
- 榜单乱序/重复事件、结算重试、期次切换后余额保留及进度隔离。
- 结算补发、自动补缺款、未开奖资格不开奖；弹幕故障不影响资产。

测试以领域规则单元测试、核心数据库事务集成测试及关键端到端场景为主，并覆盖消息重复、延迟、服务重启和响应超时后重试。

进入详细设计前需确认：生产是否继续沿用新账号1亿花瓣的初始化规则；首期活动生效配置；首期部署环境和规模。未明确变更前，业务实现与验收以需求文档为准，不自行修正文案差异或增加新玩法。
