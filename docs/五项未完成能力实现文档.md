## 5. 详细设计

### 5.1 Redis 撤销缓存与 BigCache 负缓存

**目标**：严格撤销模式下，Redis 命中可快速拒绝已撤销会话；BigCache 只缓存“该 sid 当前不在 Redis 黑名单”2 秒，避免短时重复查询 Redis。**任何缓存命中都不能跳过 MySQL**；Redis 丢失不能恢复已退出会话。

**应用端口**（`identity/application`）：

```go
type RevocationStore interface {
    // true=确定已撤销；err=Redis 依赖故障。调用方不得把 err 当作“未撤销”。
    Revoked(ctx context.Context, sid string, tokenExpiry time.Time) (bool, error)
    // 提交后尽力写 Redis，失败不改变业务结果。
    MarkRevoked(ctx context.Context, sid string, sessionExpiresAt time.Time) error
    // 删除本机负缓存。
    Forget(sid string)
}
```

`Service` 增加 `Revocations RevocationStore`；`cmd/server/main.go` 组装基础设施实现。

**Redis + BigCache 实现**：`identity/infrastructure/cache/revocation.go`

- Redis key：`identity:revoke:sid:{sid}`，值 `"1"`；TTL 为会话 `expires_at + 30s`。
- BigCache 配置：`LifeWindow=2s`、`CleanWindow=1s`、`HardMaxCacheSize=16` MiB、`Shards=256`；值保存 `expires_at` 与 `cached_at`，读取时自行判断过期。
- 键使用完整 `sid`；`Put` 截止时间取 `min(now+2s, tokenExp)`；容量满/初始化失败视为普通未命中。
- `Revoked`：
  1. BigCache 命中且未过期：返回 `false,nil`，不查 Redis。
  2. 否则查 Redis：`redis.Nil`=未撤销，写负缓存；值 `"1"`=已撤销，删除负缓存并返回 `true`；其他错误原样返回，不写负缓存。
- `MarkRevoked`：剩余 TTL ≤0 直接返回；`SET key 1 PX ttl`；删除本机负缓存。
- `Forget`：删除 BigCache 项，忽略不存在。

**校验顺序（`Service.Introspect`）**：

1. 验 Access JWT，拿到 `sid`、`exp`。
2. 调 `Revocations.Revoked`。
   - 返回 `true`：立即 `401 INVALID_SESSION`。
   - 返回 error：**记录告警并继续查 MySQL**（设计文档明确“现有 Access 校验可仅使用 MySQL”），不写负缓存。
3. **无论负缓存/Redis 结果如何，都执行 `Repo.SessionAccount`**，校验 `revoked_at`、`expires_at`、账号 `ACTIVE`、token subject 绑定。
4. 若 MySQL 发现已撤销且未过期：尽力 `MarkRevoked` 回填 Redis，返回 `401 INVALID_SESSION`。
5. 若 MySQL 不可用：返回 503；不能仅凭 JWT 或缓存放行。

**退出/重放**：

- `Service.Logout` 验 Refresh JWT 后调用 `Repo.Revoke`；提交成功后删除本机负缓存，并用 1 秒独立超时尽力写 Redis；Redis 失败只告警，退出仍成功。TTL 使用 Refresh claims 的 `exp + 30s`。
- `mysql.Repository.Rotate` 检测到 Refresh 哈希不匹配时先提交撤销，并返回 `Rotation{ExpiresAt, Replayed:true}`；`Service.Renew` 捕获后执行 `MarkRevoked` + `Forget`，再返回 `401 REFRESH_REPLAY`。不得因 Redis 失败把重放当成成功。
- 禁用账号当前无公开接口；`Introspect` 的 MySQL 状态校验已覆盖。后续实现禁用时按同一方式逐会话写 Redis。

**失败语义**：

| 故障 | 行为 |
|---|---|
| Redis 不可用 | 注册/登录/刷新仍按现有逻辑 503（限流依赖 Redis）；既有 Access 校验退回 MySQL；退出仍以 MySQL 为准 |
| BigCache 不可用/满 | 绕过本机缓存，正常查 Redis/MySQL |
| MySQL 不可用 | 鉴权/刷新 503，不能仅凭 JWT 或缓存放行 |
| Redis 重启/键被淘汰 | MySQL 仍拒绝已撤销会话；可按查询结果回填 |

**测试**：

- 单元（fake store/clock）：负缓存命中仍调用 MySQL；Redis=`"1"` 拒绝；Redis error 不被当成未撤销；MySQL 撤销优先；TTL 计算；Redis 失败时 logout 仍成功；重放写缓存。
- BigCache：真实实例验证 TTL、过期即未命中、容量上限不阻塞。
- 集成（`IDENTITY_TEST_REDIS_ADDR` 可选）：logout 写键；flush Redis 后旧 Access 仍 401；并发 refresh/logout 最终撤销。
- 不引入 miniredis；保持项目“真实 Redis 才跑集成”的约定。

### 5.2 gRPC 资料接口

**契约**：`contracts/rpc/identity/v1/profiles.proto`

```proto
syntax = "proto3";
package activity.identity.v1;
option go_package = "activity/contracts/rpc/identity/v1;identityv1";

service IdentityService {
  rpc BatchGetPublicProfiles(BatchGetPublicProfilesRequest)
      returns (BatchGetPublicProfilesResponse);
}
message BatchGetPublicProfilesRequest {
  repeated string user_ids = 1; // 十进制字符串，最多 100，允许重复
}
message PublicProfile {
  string user_id = 1;
  string display_name = 2; // nickname 非空优先，否则 account_name
}
message BatchGetPublicProfilesResponse {
  repeated PublicProfile profiles = 1; // 不存在的用户不返回
}
```

- 采用字符串 ID 与现有跨服务契约约定一致，避免精度歧义；服务端用 `platform.UID` 校验并去重。
- 只返回公开字段，绝不返回密码/会话/账号状态/资产。

**代码生成**：

- 根目录 `contracts/rpc/buf.yaml`、`buf.gen.yaml`；生成到 `contracts/rpc/identity/v1/`，**生成文件提交仓库**，正常构建不依赖 protoc/buf。
- 本机未安装工具；M0 安装固定版本（`buf`、`protoc-gen-go`、`protoc-gen-go-grpc`），或使用一次性 Docker protoc 镜像。增加 `scripts/Generate-Rpc.ps1`，改 proto 后必须重新生成并提交。
- 根 `go.mod` 增加 `google.golang.org/grpc`、`google.golang.org/protobuf`；identity/ranking 的 `go.mod` 增加 grpc 依赖并 `go mod tidy`/`go work sync`。

**identity 服务端**：

- 新增 `internal/identity/interfaces/grpc/server.go`、`interceptor.go`。
- application 增加 `PublicProfiles(ctx, ids []string) ([]domain.PublicProfile, error)`：
  - 空输入返回空；非法 ID `400 INVALID_REQUEST`；超过 100 个唯一 ID 拒绝；按输入顺序去重。
  - SQL：`SELECT CAST(user_id AS CHAR), COALESCE(NULLIF(nickname,''), account_name) FROM account WHERE user_id IN (...)`；缺失用户省略。
- 删除 HTTP `POST /internal/identity/v1/profiles`；handler 不再直接调用仓储。
- 独立监听 `GRPC_ADDR`（默认 `:9090`）；一元拦截器校验 metadata `x-internal-token` 与 `INTERNAL_TOKEN` 常量时间相等，长度 <32 或缺失返回 `Unauthenticated`；消息上限 1 MiB。健康检查方法（`grpc.health.v1.Health/Check`、`Watch`）豁免内部 token，否则探针无法使用；业务方法一律校验。

- 本地不启用 TLS；生产通过 `GRPC_TLS_CERT_FILE/GRPC_TLS_KEY_FILE` 启用，跨主机必须 TLS。Nginx 不暴露 gRPC。

type ProfileProvider interface {

- `domain` 不导入 `application`/`infrastructure`/`gin`/`database/sql`/`uow`。
- `application` 定义仓储端口（方法参数 `uow.Tx`），只依赖 domain、`uow`、纯技术端口；可导入其他上下文 **application** 端口。
- `infrastructure/mysql` 实现 application 端口和 UoW；可导入 application 的错误/DTO。
- `interfaces` 只调用 application；`cmd/server` 是组合根。
- 允许 `participation/domain -> lottery/domain`；禁止反向。`lottery/application` 可导入 `participation/application` 与 `assets/application`；`assets/application` 通过小接口 `ParticipationGuard` 反向接收实现，避免循环。

**UnitOfWork 端口**（`internal/uow/uow.go`）：

```go
type Result interface{ RowsAffected() (int64, error) }
type Row interface{ Scan(dest ...any) error }
type Rows interface {
    Next() bool; Scan(dest ...any) error; Err() error; Close() error
}
type Tx interface {
    Exec(ctx context.Context, query string, args ...any) (Result, error)
    Query(ctx context.Context, query string, args ...any) (Rows, error)
    QueryRow(ctx context.Context, query string, args ...any) Row
}
type Options struct{ ReadOnly bool }
type UnitOfWork interface {
    Within(ctx context.Context, opts Options, fn func(context.Context, Tx) error) error
}
var ErrCommitUnknown = errors.New("commit outcome unknown")
```

- MySQL 实现负责 Begin/Commit/Rollback；提交失败包装 `ErrCommitUnknown`；回调错误则回滚并返回原错误。
- 仓储方法接收 `uow.Tx`，不得自行开启/提交事务；application/domain 不出现 `*sql.Tx`。
- `uow/mysql/batch.go` 提供多值 INSERT；`uow/mysql/outbox.go` 提供接受 `uow.Tx` 的 Outbox 写入。

**事务、锁与幂等**：

- 每个变更命令由 application 获取 Redis 用户锁 `activity:{env}:user:{id}:mutation`（`SET NX PX`，唯一 token，不等待）；失败 `409 OPERATION_IN_PROGRESS`；释放用 token 校验 Lua。
- 一个 `uow.Within` 事务；锁顺序固定：`activity_edition FOR SHARE` → `wallet FOR UPDATE NOWAIT` → `user_participation FOR UPDATE` → `user_round FOR UPDATE` → 具体记录（多行按 `grant_id` 排序）。
- 抽奖先只读恢复幂等结果，再获取锁；`idempotency_request` 请求哈希、24 小时窗口、成功映射保持原算法。

### 5.4 批量写入与结算游标/租约

#### 5.4.1 批量写入

新增 `internal/uow/mysql/batch.go`：

```go
type BatchSpec struct {
    Table           string
    Columns         []string
    MaxRows         int // 默认 100
    MaxBytes        int // 默认 512 KiB
    MaxPlaceholders int // 默认 60000
}
func Insert(ctx context.Context, tx uow.Tx, spec BatchSpec, rows [][]any) error
```

- 生成 `INSERT INTO table(cols) VALUES (?,...),(?...)`；按行数、估算字节数、占位符数三者取最小分块。
- 所有分块串行使用同一个 `uow.Tx`；禁止 goroutine 共用事务连接；任一分块失败立即返回，外层事务整体回滚。
- 列名仅来自编译期常量；空输入返回 nil。
- 应用位置：
  - `draw_detail_{shard}`：正常 ≤30、预览确认 ≤180。
  - `flower_lit_log_{shard}`：≤18，仅正增量。
  - `reward_grant`：≤30/≤180，含阶段/宝箱/排名奖励。
  - `wallet_ledger`：抽奖/购买 4–7 条，在事务末尾合并写入。
  - `ranking_award`、`outbox_event`（ranking 结算）最多 30 对；排名奖励 outbox 的 `event_id` 直接使用 `award_id`，使重复冻结幂等。
- 钱包变更策略：`ApplyChanges` 先在内存计算各步余额并校验非负/溢出，执行一条条件 `UPDATE wallet` 更新最终余额、`ledger_seq`、`version`，再批量插入带 `balance_after`/`entry_no`/`user_ledger_seq` 的流水；受影响行必须为 1。
- 行粒度、唯一键、CHECK 和幂等含义不变；`draw_order`、`idempotency_request`、状态更新仍单条。

#### 5.4.2 activity 结算任务

迁移 `services/activity-service/migrations/004_settlement_scheduling.sql`：

```sql
USE activity_core;
ALTER TABLE settlement_task
  ADD COLUMN next_retry_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) AFTER lease_until,
  ADD KEY idx_task_claim (status, next_retry_at, lease_until);
ALTER TABLE activity_edition
  ADD KEY idx_edition_settlement (settlement_status, ends_at);
```

任务步骤（零填充保证字典序即依赖序）：

| step | partition_no | 作用 |
|---|---|---|
| `01_CLOSE_EDITION` | -1 | 锁期次 `FOR UPDATE`，等待所有持有 `FOR SHARE` 的已接纳事务提交（排空），确认已结束，置 `ENDED`，幂等 |
| `02_SETTLE_USERS` | 0..3 | 按 `MOD(user_id,4)` 分片，分批结算用户 |
| `03_RANKING` | -1 | 调 ranking 结算，等待回执 |
| `04_FINALIZE` | -1 | 所有前置任务完成且 ranking COMPLETED 后置期次 COMPLETED |

- 每个到期期次创建 7 行（1+4+1+1），`INSERT ... ON DUPLICATE KEY UPDATE` 幂等；`activity_edition.settlement_status` 置 `RUNNING`。
- 领取查询在短事务中执行：

```sql
SELECT edition_id, step, partition_no, retry_count, cursor_json
FROM settlement_task t
WHERE t.status IN ('PENDING','RUNNING')
  AND (t.lease_until IS NULL OR t.lease_until < UTC_TIMESTAMP(6))
  AND t.next_retry_at <= UTC_TIMESTAMP(6)
  AND NOT EXISTS (
      SELECT 1 FROM settlement_task p
      WHERE p.edition_id=t.edition_id AND p.step<t.step AND p.status<>'COMPLETED'
  )
ORDER BY t.edition_id, t.step, t.partition_no
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

  随后 `UPDATE ... SET status='RUNNING', lease_owner=?, lease_until=now+60s WHERE ...`；完成/重试更新必须带 `lease_owner` 和 `status='RUNNING'` 且 `RowsAffected()==1`，丢失租约不得假设成功。
- `02_SETTLE_USERS`：
  - 读取 `cursor_json={"after_user_id":"..."}`，默认 `0`；每页 100 个用户：
    ```sql
    SELECT CAST(user_id AS CHAR) FROM user_participation
    WHERE edition_id=? AND MOD(user_id,4)=? AND user_id>?
    ORDER BY user_id LIMIT 100;
    ```
  - 逐用户调用 `participation/application.SettleUser`（独立事务 + Redis 用户锁）。
  - 整页成功后持久化最后 user_id；恰好 100 条则任务回 `PENDING` 继续下一 tick，少于 100 条则 `COMPLETED`。
  - 任一用户失败则不推进游标；已提交用户由现有 stage/chest/select 幂等保证可重试。
  - 瞬时错误（`OPERATION_IN_PROGRESS`、锁冲突、依赖 5xx）：`status='PENDING'`，`retry_count++`，`last_error` 截断 1024，`next_retry_at=now+min(5s*2^n,5m)`。
- `03_RANKING`：
  - 调用 `POST /internal/ranking/v1/settle`（15s 超时），解析 `{"status":"...","pending_awards":N}`；不持有数据库事务。
  - `COMPLETED` → 任务完成；`FAILED`/对账 409 → 终态 `FAILED`；其他状态 → `PENDING`，5s 后重试。
- `04_FINALIZE`：确认同 edition 所有任务 `COMPLETED` 且 ranking 任务完成，才置 `activity_edition.settlement_status='COMPLETED'`。
- 排空说明：用户事务在开始时对 `activity_edition` 持 `FOR SHARE` 直到提交；`01_CLOSE_EDITION` 的 `FOR UPDATE` 会阻塞到这些事务结束。close 提交后新请求读到 `ENDED` 被拒绝，因此后续 `02_SETTLE_USERS` 不再需要额外的事务登记表。
- `FAILED` 为终态，不自动领取；提供 SQL 手动重排队说明（`status='PENDING', retry_count=0, next_retry_at=UTC_TIMESTAMP(6)`）。
- `Maintenance` 改为每 5 秒 `ensureTasks` + 领取/执行一个任务；不再全量扫描参与者、不再直接调用 ranking。

#### 5.4.3 ranking 可恢复结算

迁移 `services/ranking-service/migrations/002_settlement_resume.sql`：

```sql
USE activity_ranking;
ALTER TABLE ranking_settlement
  ADD COLUMN cursor_json JSON NULL,
  ADD COLUMN lease_owner VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NULL,
  ADD COLUMN lease_until DATETIME(6) NULL,
  ADD COLUMN retry_count INT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN next_retry_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  ADD COLUMN last_error VARCHAR(1024) NULL,
  ADD KEY idx_settlement_claim (status, next_retry_at, lease_until);
```

状态机：`PENDING → RECONCILING → FROZEN → AWARDING → COMPLETED`；对账不一致/重试耗尽 → `FAILED`。

`Advance(ctx, edition)`（application）流程：

1. Upsert `ranking_settlement`（默认 `PENDING`，`INSERT ... VALUES(?, JSON_OBJECT(), JSON_OBJECT('version',1)) ON DUPLICATE KEY UPDATE edition_id=edition_id`，不得覆盖已有状态/cursor），随后带租约领取：
   ```sql
   UPDATE ranking_settlement
   SET lease_owner=?, lease_until=now+60s,
       status=IF(status='PENDING','RECONCILING',status)
   WHERE edition_id=? AND status NOT IN ('COMPLETED','FAILED')
     AND (lease_owner IS NULL OR lease_until<UTC_TIMESTAMP(6));
   ```
   受影响 0 行则返回当前状态（busy），不视为失败。
2. `RECONCILING`：读 `cursor_json`：
   ```json
   {"manifest_after":"123","current_user":"456","facts_after":"7","participants":N,"facts":M}
   ```
   按页（100）拉 activity manifest/facts；每个用户先消费 `ParticipationInitialized.v1`，再按 `facts_after` 消费 `FormalDrawCommitted.v1`；核对 `score`/`last_contiguous_seq`。每页/每用户提交后持久化 cursor；时间预算（约 5s）用尽也保存并释放租约。manifest 耗尽 → `FROZEN`、写 `frozen_at`、核对计数/校验和、清 cursor。
3. `FROZEN`：一个事务内：
   - 锁 settlement 行；`INSERT IGNORE ranking_snapshot ... SELECT ROW_NUMBER()`。
   - 读 Top20，内存生成奖励；`INSERT IGNORE ranking_award` 批量写入。
   - 批量写 `outbox_event`，`event_id=award_id`，事件 `RankingAwardRequested.v1`。
   - 置 `AWARDING`；提交。
4. `AWARDING`：统计 `ranking_award.delivery_status='PENDING'`；为 0 则置 `COMPLETED`、`completed_at`；否则释放租约返回 `AWARDING`。
5. 重复调用：`COMPLETED` 直接成功；`FROZEN` 重入时 `INSERT IGNORE` 不重复；`FAILED` 返回终态。

- 冻结后新事实：`Consume` 在同一事务中检查 settlement 状态，若为 `FROZEN/AWARDING/COMPLETED`，新 draw 事实返回 `409 SETTLEMENT_FROZEN`；已存在重复事实仍幂等。
- HTTP `/internal/ranking/v1/settle` 对已持久化状态返回 200 + `{status,pending_awards}`；终态对账冲突返回 409；依赖错误 5xx。
- 保留“activity 不直接读 ranking 库、ranking 通过 internal HTTP 拉取事实”的边界。
- `cutoff_manifest` 保存核对计数/校验信息；cursor 只记录已提交进度。

## 8. 风险与回滚

| 风险 | 缓解/回滚 |
|---|---|
| DDD 重构行为回归 | 按用例小步迁移；每步保留旧适配器直到新路径通过 e2e；不双写业务规则；单提交可回滚 |
| 锁顺序错误/死锁 | 集中 `mutation.go` 加载；记录型 fake 验证顺序；MySQL 并发测试；禁止 wallet 先于 edition |
| 提交结果未知 | 不发布效果、不生成新 ID；新连接重读幂等/订单；找不到返回 `OPERATION_RESULT_UNKNOWN` |
| gRPC 工具链缺失 | 生成代码提交；M0 固定安装脚本/Docker 生成；构建不依赖 protoc |
| 删除 HTTP profiles 影响未知调用方 | 删除前全仓检索；仓库内仅 ranking；如外部调用需单独确认并保留一个版本周期 |
| H5 多标签刷新 Replay | Web Locks 串行 + 单飞；Cookie 共享；并发测试；失败统一重新登录 |
| Cookie/CSRF 本地开发跨源 | 统一经 Nginx 同源；Vite 代理改写 Origin 或设置 5173 的 ALLOWED_ORIGIN |
| 已有数据卷缺新列 | 增量迁移 + 备份后手动执行；禁止删卷；服务启动检查列缺失并明确报错 |
| 结算游标与提交不一致 | cursor 只在业务事务提交后更新；重放由幂等键保证；崩溃最多重做一页 |
| 结算任务饥饿/乱序 | 零填充步骤名 + 前置任务检查；FAILED 终态需人工重排 |
| late fact 污染冻结快照 | 冻结后拒绝新事实 `SETTLEMENT_FROZEN`；重复事实幂等 |
| 批量 INSERT 包大小超限 | MaxRows/MaxBytes/MaxPlaceholders 三重分块；180 抽测试 |
| profile RPC 故障拖慢 board | 200ms 截止 + 60s 缓存 + 占位；内部鉴权错误上抛，其余降级 |
| Nginx 服务旧 dist | 构建后再 compose；保留上一版 dist 便于回滚 |
| 结算大期次快照压力 | 本计划不承诺无限规模；上线前压测快照/对账/回执链路 |

**回滚策略**：

- identity 缓存：`REVOCATION_CACHE_ENABLED=false` 应急绕过（仍查 MySQL）；不是兼容 API。
- gRPC：回滚 identity 服务端/ranking 客户端提交，恢复 HTTP profiles 路由与调用；proto/生成文件可保留。
- activity 拆分：代码回滚；无 schema 变更（结算列除外）。
- 结算：`SETTLEMENT_ENABLED=false` 停止调度；任务保留可恢复；additive 列旧代码可忽略。
- H5：后端保持新 API；回滚为上一版 dist 或恢复 Nginx 旧配置；按决策不保留 `/api/v1` 回退层。
- 数据库：不删除新列/表；旧代码可忽略。
