# Activity 持久层设计方案 V2

本设计记录持久层的逻辑模型。业务口径见 [Lottery 业务需求](Lottery业务需求文档（不含后台）.md)。整点榜单新增的窗口、水位和奖项记录见 [整点榜单结算](整点榜单结算.md)。

实际字段、类型及约束以各服务的 `migrations/` 为准。MySQL 8.4 初始化、升级及核验步骤见 [本地部署](../deploy/local/README.md)。

## 1. 总体决策

- 保持账号、活动核心、榜单、通知四服务；按数据所有权垂直划分逻辑库。
- 活动核心库使用同一个 MySQL 实例和事务连接。仅对指定的大记录表做4张水平分表，不跨实例分片，不引入数据库代理。
- 分表规则固定为 `suffix = user_id % 4`，后缀为 `_0`、`_1`、`_2`、`_3`，仓储层统一路由。
- 抽奖批次、逐抽结果、独立点亮流水、奖励明细、资产流水分别保存。它们是不同的业务事实，不能互相取代。
- Redis 用于限流、缓存和榜单加速；余额、业务结果、预览和幂等事实以 MySQL 为准。

|服务|逻辑库|职责|
|---|---|---|
|identity-service|`activity_identity`|账号、认证会话、账号创建事件|
|activity-service|`activity_core`|期次与规则、资产、购买、进度、抽奖与预览、奖励及结算编排|
|ranking-service|`activity_ranking`|积分事实投影、排名、最终快照及发奖清单|
|notification-service|不设业务事实库|订阅 Redis Pub/Sub，通过 SSE 推送实时弹幕|

账号、活动核心和榜单逻辑库各部署在独立 MySQL 实例，各服务只连接并访问自己的库。活动核心的四组分表使用活动实例内的本地事务。

## 2. 相对 V1 的必要修订

|最新版需求|本方案调整|
|---|---|
|独立逐抽点亮流水|新增 `flower_lit_log_0..3`，与批次、进度共同事务提交|
|抽奖结果不可因选款改变|保存不可变逐抽快照；选款只改奖励明细|
|每实际抽次有奖励明细|`reward_grant` 按抽次生成，不只保存批次奖励汇总|
|资产变化原因分别保留|扣费、金币中奖、花瓣中奖、退款分别记流水；中奖按批次汇总|
|普通抽奖重试限制24小时|请求保存参数摘要、首次接纳时间及恢复截止时间；过期拒绝，不重新执行|
|先抽后付申请180次、按实际收费|同时保存申请与实际次数，预收为实际费用，退款为0|
|宝箱普通戒指开奖即获得|奖励已获得与宝箱未确认允许同时存在|
|登录与注册限流修订|Redis 分别维护账号失败计数与注册IP计数，遵守各自计时规则|

## 3. 水平分表范围

|逻辑表|物理表|是否分表|原因|
|---|---|---|---|
|抽奖批次 `draw_order`|`draw_order_0..3`|是|随抽奖请求增长，主要按用户查询|
|逐抽结果 `draw_detail`|`draw_detail_0..3`|是|每实际抽次一行，增长最快|
|点亮流水 `flower_lit_log`|`flower_lit_log_0..3`|是|独立逐抽点亮事实，按用户及期次查询|
|资产流水 `wallet_ledger`|`wallet_ledger_0..3`|是|长期追加，按用户核对资产|
|奖励明细 `reward_grant`|`reward_grant`|否|本期保留单表，简化待选处理、历史持有查询及结算；按抽次保存仍可能快速增长，必须纳入容量监控|
|钱包、用户参与、轮进度、购买、预览、宝箱、阶段领取|原表名|否|本期聚焦状态与事务正确性|
|Outbox、Inbox、操作幂等、结算任务|原表名|否|有独立调度和保留策略，不套用用户流水路由|

分4张主要控制单表与索引规模，不表示整体写入能力提高4倍。奖励表暂不分是延续本轮已讨论的范围，不是认为它是小表；若实测它成为瓶颈，再单独评审按用户4分表。

所有分表行均冗余保存 `user_id`；同用户所有期次使用同一后缀。关联使用 `(user_id, 业务ID)`，不能仅凭抽奖单号、流水号或自增ID猜测分片。消息与内部任务也携带用户ID。

例如 `user_id=10003`，本次交易访问 `wallet`、`user_round`、`reward_grant` 和后缀 `_3` 的四类记录表，仍是一笔本地事务。

## 4. 账号库与限流

|表|主要字段|关键约束|
|---|---|---|
|`account`|`user_id, account_name, password_hash, nickname, status, created_at, updated_at`|账号名唯一并区分大小写，密码以散列保存|
|`login_session`|`session_id, user_id, refresh_token_hash, expires_at, revoked_at`|会话ID唯一；支持续期、退出和撤销，不保存明文令牌|

Redis 注册计数按来源IP：先校验格式，再检查频率，通过后计数；重复账号等失败计入，通过计数后有效期从本次起60秒，累计3次后拒绝后续尝试；白名单绕过这项限制。

登录失败按账号计数，达到5次后在限制窗口拒绝；每次失败计数的有效期从最后一次计数起15分钟，成功清除。计数与有效期更新需原子执行；账号不存在与密码错误统一返回凭据错误，不对外暴露区别。

账号创建事件与账号同事务写入 Outbox；核心库按用户唯一初始化钱包。资产未初始化的访问需等待或补偿初始化，不得再次赠送。会话实现及限流数据不是用户资产事实。

## 5. 核心库：配置、资产与购买

### 5.1 期次与规则

|表|主要字段|关键约束|
|---|---|---|
|`activity_edition`|`edition_id, activity_code, name, starts_at, ends_at, status, active_rule_version, settlement_status`|参与状态与结算完成状态独立|
|`activity_rule_version`|`edition_id, version, schema_version, rule_json, checksum, created_at`|期次与版本唯一；引用后不可覆盖|
|`item_definition`|`item_id, type, name, icon_url`|道具基础信息；不承担真实背包、穿戴或过期回收|

规则沿用版本化 JSON 的初步建议，包含奖池权重、花朵概率与保底、阶段与宝箱奖励、候选款式、商店和排名奖励；结构与引用必须校验，不用浮点表示权重。没有后台编辑需求，暂不拆一套配置管理表。

抽奖单、轮进度、预览均记录所用规则版本。期内配置如何切换尚未最终确认；建议每轮绑定版本、下轮使用生效版本，预览固定使用生成时版本。该项是设计建议，不冒充现有业务规则。

### 5.2 钱包与独立资产流水

|表|主要字段|关键约束|
|---|---|---|
|`wallet`|`user_id, gold_balance, petal_balance, ledger_seq, version, updated_at`|用户主键；账号级，余额非负；换期不清空|
|`wallet_ledger_s`|`ledger_id, user_id, edition_id?, asset_type, delta, balance_after, reason, biz_type, biz_id, entry_no, user_ledger_seq, created_at`|`s=user_id%4`；唯一 `(user_id,biz_type,biz_id,entry_no)` 与 `(user_id,user_ledger_seq)`|
|`purchase_order`|`order_id, user_id, edition_id, request_id, type, product_code, gold_cost, petals_granted, rule_version, parent_confirm_id?, created_at`|用户与购买请求号唯一；成功结果与资产共同提交|
|`purchase_quota`|`user_id, edition_id, product_code, order_id`|前三项唯一；只占用当期限购档及模拟礼包资格|

`edition_id` 在注册发放时可为空；全局递增的用户流水序号来自受锁钱包，同一业务内部按明确顺序生成各行。`balance_after` 为该条变化之后对应资产的余额，最后一条应与钱包一致，不是把所有行都填成最终余额。

普通30连抽的流水示意：申请扣费 `-150花瓣` → 本批金币中奖汇总 → 本批花瓣中奖汇总 → 未执行退款 `+40花瓣`。实际消耗110花瓣。零变更不写流水，汇总中奖不能省掉不同变化原因。

先抽后付示意：必要时扣补差金币 → 加补差花瓣 → 按实际N抽扣花瓣 → 本批中奖分类入账；申请180次但只实际执行N次，未预收的部分不写退款流水。购买、礼包、补差仅保存购买与资产事实，不伪装成中奖奖励明细。

Activity 初始化钱包时，同一事务记录金币及花瓣的初始发放流水。旧 Lottery 的初始花瓣流水缺口保留为历史口径。参见 [钱包初始化实现](../services/activity-service/internal/assets/infrastructure/mysql/transaction.go)。

## 6. 核心库：参与、阶段和宝箱

|表|主要字段|关键约束|
|---|---|---|
|`user_participation`|`user_id, edition_id, current_round_no, formal_draw_count, draw_seq, draw_progress_version, version, created_at`|用户与期次唯一；串行化当期进度，正式抽奖次数含预览兑现|
|`user_round`|`user_id, edition_id, round_no, rule_version, flower_count, consumed_gold_equivalent, unlocked_chests, completed_chests, claimed_stage_mask, status, started_at, completed_at`|用户、期次、轮号唯一；新轮新增行，保留旧轮|
|`stage_claim`|`claim_id, user_id, edition_id, round_no, stage_code, reward_grant_id, claim_source, claimed_at`|用户、期次、轮号、阶段唯一；来源区分主动领取与结束补发|
|`chest_open`|`chest_id, user_id, edition_id, round_no, chest_no, candidate_code, reward_type, candidate_snapshot, reward_grant_id, status, opened_at, confirmed_at`|轮内箱号唯一，轮内候选代码唯一；防止重复开奖与放回|

轮状态保存已领阶段位图，`stage_claim` 保存业务关联，两者在同一事务更新。花朵数0～18；累计消耗是实际花瓣消耗×60，不是额外金币扣款。

宝箱未开奖资格只体现在 `unlocked_chests`，不创建随机结果；开奖时写 `chest_open` 和奖励。普通戒指奖励立即为 `OBTAINED`，箱子仍为 `OPENED`；选择权奖励为 `PENDING_CHOICE`，选款后为 `SELECTED`，随后确认箱子才变为 `CONFIRMED` 并增加完成次数。重复进入读取原结果。

下一轮检查18朵、全部宝箱确认、阶段全领和阶段选择权已选；不增加普通抽奖来源待选权益必须清空的条件。余额及期内积分保留。

## 7. 核心库：抽奖批次、逐抽与点亮流水

|表|主要字段|关键约束|
|---|---|---|
|`draw_order_s`|`draw_id, user_id, edition_id, round_no, operation_id, mode, preview_id?, pool_code, rule_version, requested_count, actual_count, charged_petals, refunded_petals, consumed_petals, flowers_added, reward_snapshot_json, draw_seq, occurred_at`|用户与操作标识唯一；用户与非空预览ID唯一；用户、期次与draw_seq唯一|
|`draw_detail_s`|`detail_id, user_id, edition_id, draw_id, draw_no, original_reward_code, original_item_name, quantity, petal_cost, flowers_before, probability_lit, guarantee_lit, flowers_after, cumulative_gold_equivalent`|`(user_id,draw_id,draw_no)` 唯一；每实际抽次一行|
|`flower_lit_log_s`|`log_id, user_id, edition_id, round_no, draw_id, draw_no, pool_code, flowers_added, flowers_after, created_at`|`(user_id,draw_id,draw_no)` 唯一；仅点亮数大于0时插入|

`s` 是物理后缀占位符，所有分表字段与索引保持一致。

批次 `reward_snapshot_json` 是按抽次排序的不可变原始奖励快照；逐抽表用于结构化核对，和快照从同一份执行结果生成并共同提交。每个实际抽次都有奖品，即使没有点亮；未执行抽次没有奖品明细。后续选款不能回写历史快照和原始逐抽结果。

点亮流水独立存在：本抽概率加保底合计点亮3朵，只写一行 `flowers_added=3`；10抽仅第2、7抽点亮，则仅写两行且 `draw_no=2、7`。开启新轮不覆盖历史，预览和放弃不写正式流水。

费用与次数约束：

|模式|申请次数|预先扣费|退款|实际计分与保底|
|---|---|---|---|---|
|普通抽奖|1/10/30|申请次数×单价，余额必须事先足额|未执行次数×单价|实际次数×单价|
|先抽后付兑现|180|实际次数×白昼单价|0|实际次数×白昼单价|

两种模式都保存真实申请次数、实际次数及点亮总数，不能把预览兑现的申请次数改成N。

## 8. 核心库：预览、奖励与操作幂等

### 8.1 固定预览

`preview_order`：`preview_id, user_id, edition_id, round_no, rule_version, start_progress_snapshot, start_progress_version, requested_count=180, actual_count, required_petals, result_json, expected_progress_json, result_hash, status, confirmed_draw_id?, created_at, confirmed_at?, abandoned_at?`。

用户与期次唯一；状态 `PENDING → CONFIRMED / ABANDONED`，未生成记录即无已用资格。保存逐抽结果及预计终态，不只保存奖励汇总，不设30分钟过期字段。预览起点版本仅随正式抽奖/轮进度变化更新，不因查余额或领取普通奖励变化而无故失效。

生成、确认、放弃均检查活动进行中；当前期可读取已有预览。确认在事务中检查无其他正式抽奖且起点一致，补差和原结果兑现共同提交。普通抽奖不受“存在预览”阻止，但会使原预览无法确认。结束结算不主动把待确认预览改为过期。

### 8.2 独立奖励明细

`reward_grant`：`grant_id, user_id, edition_id, round_no?, source_type, source_id, source_entry_no, draw_id?, draw_no?, original_reward_code, original_item_name, quantity, candidate_snapshot?, status, final_item_id?, final_item_name?, created_at, updated_at, selected_at?`。

- 唯一 `(user_id,source_type,source_id,source_entry_no)`；普通抽奖来源区分白昼、星夜，另有先抽后付、阶段、宝箱、榜单来源。
- 每实际抽次一条奖励，金币/花瓣中奖也保存；阶段、宝箱与榜单按奖励项保存。每份可选权益单独一行，候选及名称保存当时快照。
- 状态明确区分 `OBTAINED`（已获得）、`PENDING_CHOICE`（待选择）、`SELECTED`（已选择）。选款条件更新原行并填最终道具，不另发一份选择权；重复同款确认返回原结果，已选其他款不能改选。
- 普通奖励创建时即填 `final_item_id/final_item_name`；选择权待选时这两项为空，选款时填写。原始奖励代码、名称和候选快照保留不变，保证汇总与历史追溯各有明确数据来源。
- 资产流水按批次汇总，因此一条中奖流水可以对应多条奖励；用 `biz_type+biz_id` 关联批次，再按资产类型核对汇总，不要求逐抽写资产流水。
- 宝箱未确认的普通戒指已计入获得奖励；召唤确认状态只由宝箱记录表达。待选宝箱权益也可进入召唤记录展示。

### 8.3 普通抽奖24小时重试

`idempotency_request`：`user_id, operation_type, operation_id, request_hash, accepted_at, recover_until, status, result_user_id, result_draw_id, created_at`；前三项联合唯一。

普通抽奖处理规则：先查原请求；相同参数且在有效期内，读取原批次及原快照，不能用当前选款状态重造结果；不同参数拒绝；过24小时拒绝恢复，也不得当成新请求重新扣费。成功重放不受当前余额、进度变化影响，且不重新检查为一笔新交易。

本稿建议以服务端首次接纳该有效操作的时间计算24小时，准确起点需在接口设计时确认。摘要覆盖期次、奖池、抽数和模式等业务参数，操作标识不跨期复用。

请求登记与成功业务结果共同提交，失败不遗留已成功标记。并发重复请求通过唯一约束及用户操作互斥处理。已成功请求过期后保留紧凑的拒绝复用记录，不能仅删除24小时缓存，否则旧标识会被重新接纳；未来若要清理这些记录，需先设计可验证有效期的操作标识协议。

其他购买、领取和选款保留自然业务唯一约束；不把普通抽奖24小时规则套给长期可恢复的预览、奖励和宝箱。

## 9. 索引与查询映射

以下为逻辑索引列顺序，最终 DDL 再核对类型、长度及执行计划；所有4分表执行相同迁移。

|查询|数据源及索引建议|业务口径|
|---|---|---|
|抽奖历史|`draw_order_s(user_id,edition_id,pool_code,occurred_at,draw_id)`|时间倒序，每次5批次；页面最多汇集100页，展开原快照|
|点亮页签|批次增加派生列 `has_flower`，索引 `(user_id,edition_id,has_flower,occurred_at,draw_id)`|每批总点亮数，非独立逐抽流水|
|独立点亮查询|`flower_lit_log_s(user_id,edition_id,created_at,log_id)`|时间倒序，每页20条|
|我的奖励|`reward_grant(user_id,edition_id,status,final_item_id)`|按最终ID和名称汇总已获得/已选择，排除花瓣及待选，包含金币|
|待选恢复|`reward_grant(user_id,edition_id,status,grant_id)`|恢复各来源待选权益|
|召唤记录|`reward_grant(user_id,edition_id,source_type,created_at,grant_id)`|只查宝箱，含待选；每页20条，页面最多100页|
|跨期持有查询|`reward_grant(user_id,final_item_id,status)`|跨所有期次的已获得/已选择，用于自动补缺款|
|流水对账|`wallet_ledger_s(user_id,user_ledger_seq)`|按序核对资产；按业务定位另有唯一索引|
|全期抽奖核对|`draw_order_s(edition_id,draw_id)`|逐分表扫描，补齐积分|

分页使用稳定的时间加ID顺序；接口可继续暴露需求中的页码，不新增用户页面。后台内部续扫采用游标。归属用户从认证上下文取得，不相信客户端提交的用户ID。

## 10. 榜单库与可靠通信

|表|主要字段与约束|
|---|---|
|`score_fact`|`draw_id,user_id,edition_id,draw_seq,consumed_petals,occurred_at_sec`；抽奖ID唯一，用户期次顺序唯一|
|`ranking_entry`|`edition_id,user_id,score,score_reached_at_sec,last_contiguous_seq`；用户期次唯一，包含0分记录|
|`ranking_settlement`|`edition_id,status,cutoff_manifest,reward_rule_snapshot,frozen_at,completed_at`；期次唯一|
|`ranking_snapshot`|`edition_id,user_id,final_rank,score,score_reached_at_sec`；期次用户、期次名次分别唯一|
|`ranking_award`|`award_id,edition_id,user_id,final_rank,reward_entry_no,item_id,item_name,quantity,delivery_status`；期次用户奖励项唯一|

榜单库本期不水平分表。消费正式抽奖实际消耗事件生成事实后幂等更新分数；乱序按业务序号识别缺口，达到当前分数时间由业务时间确定，不用消费时间。按分数降序、达到分数时间秒级升序、用户ID升序排序；初始化不得覆盖已有积分，0分不统一排除。

各需要可靠通信的库自有 `outbox_event(event_id,type,user_id,payload,status,retry_count,next_retry_at,created_at)`、`inbox_event(consumer_name,event_id,processed_at)`；后者联合唯一且与消费结果同事务提交。Outbox 按待投递状态与重试时间建索引，已发布历史按对账及保留策略清理，不随用户分表。

排名奖励通过契约送到核心服务，以 `award_id` 作为稳定来源ID，幂等写奖励记录。有效天数保存在规则说明快照，不新增逐条到期和自动回收。

通知事件只映射需求允许的来源：普通抽奖直接戒指、普通抽奖/先抽后付选款后的具体戒指；不扩大到阶段、宝箱或先抽后付直接戒指。包括本人消息，不按当前奖池或期次额外过滤。客户端保留200条去重和100条队列，不因此建用户消息历史表。

## 11. 事务边界与结束结算

核心用例使用同一 MySQL 事务对象传入各模块仓储，禁止模块各自开启并提交事务。所有表采用支持事务的引擎；同库不同物理表不改变原子提交范围。

普通抽奖事务：

```text
读取原幂等结果 / 尝试取得用户操作互斥
→ 校验活动与全额申请余额
→ 锁钱包、用户参与、当前轮及具体业务记录
→ 申请扣费，逐抽生成固定奖品及花朵结果，满轮中止
→ 分类累计中奖入账、未执行退款
→ 保存批次快照、逐抽明细、独立点亮流水、逐抽奖励、分类资产流水
→ 更新钱包和轮进度，登记幂等成功结果，写 Outbox
→ 提交；失败全部回滚
```

统一锁顺序为钱包→参与→轮进度→具体单据；活动截止另通过活动参与门禁协调。跨实例同用户冲突需快速拒绝，不能只是排队后让两笔不同操作都成功；具体互斥方式在实现阶段验证，唯一约束和数据库事务仍是最终保障。预览确认与放弃在同一预览状态上互斥。

活动结束结算使用 `settlement_task` 保存步骤、分片、游标、租约及重试信息，`(edition_id,step,partition_no)` 唯一：

1. 截止后停止接纳新参与，协调已接纳事务完成，为每张抽奖分表记录稳定核对边界。边界必须在交易排空后确定，不能仅凭全局ID大小或消息队列为空断言完整。
2. 按四个用户分片推进逐用户结算。已达标未领的阶段奖励与领取位图、领奖记录、资产流水在同一事务内处理。待选权益优先补齐未拥有款式，全部已拥有时选经典款；宝箱仅确认已有开奖结果。
3. 榜单服务逐分表读取本期有效正式单，按抽奖 ID 补齐 `score_fact`，核对后冻结排名并生成最终排名奖励清单。
4. 榜单发奖及回执全部完成后，活动服务标记本期结算完成。步骤可重试。参见 [活动结算编排](../services/activity-service/internal/application/settlement_worker.go) 与 [榜单结算](../services/ranking-service/internal/ranking/infrastructure/mysql/settlement.go)。

结束后查询照常；已有奖励确认是否允许按用例判断，预览生成、确认、放弃则仍要求进行中。

## 12. 容量、维护与验收

一次实际N抽，写1条批次、N条逐抽明细、N条奖励、L条点亮流水（0≤L≤N），另写有限条分类资产流水和必要事件；采用批量插入减少往返，不改变保存粒度。预览确认最多180抽，需单独测试最大事务规模。

4分表从空库同步创建，表结构变更由一个迁移模板生成4份并逐表校验。仓储只允许固定后缀表名，调用方传用户ID而不传任意表名。配置和状态表不随分片复制。

过期期次保留事实；归档先评估待选权益、历史持有查询和审计依赖，不按期次直接删除奖励和流水。4改8需要迁移、校验和切换方案，不能直接修改取模常量。记录每表行数、索引大小、增长量、写延迟和数据倾斜，并关注未分表奖励与幂等表的增长。

设计验收至少覆盖：

- 四个后缀各验证普通抽奖、预览兑现和回滚；路由不能写错用户。
- 星夜首抽点亮3朵仅一条点亮流水；部分抽次点亮保留真实批内序号。
- 批次点亮总数＝逐抽新增总数＝独立点亮流水总数；原快照不因选款变化。
- 普通30抽实际22抽：申请扣150、退40、净消耗110；先抽后付申请180实际N：扣5N、退0。
- 每实际抽次均有奖励明细；中奖资产流水可按批次汇总且原因、变更后余额正确。
- 同标识同参数24小时内恢复原结果，改参数及过期拒绝；过期记录清理不得使旧请求重新成功。
- 宝箱普通戒指奖励已获得但召唤待确认；选款更新原奖励，下一轮条件按来源检查。
- 预览不产生正式流水，放弃不产生资产；确认失败无部分结果。
- 结算扫描4分表无遗漏，重复消息/重复结算不重复加分或发奖；资产换期不重置。
